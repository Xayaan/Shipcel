# smoldot, patched for Finney

`../src/smoldot.wasm` is smoldot's light client, version 3.7.0 (tag `npm-smoldot-v3.7.0`, commit `cd98d7fa6a69e0ea66b23c0a2fb6d36c9063c4bb` of [paritytech/smoldot](https://github.com/paritytech/smoldot)), with the eight patches in this folder. Upstream smoldot can't follow Finney, for two reasons; one of its dependencies has a security advisory; and it needs more memory than a Cloudflare Durable Object has, for five.

1. **`0001-aura-from-finalized-header-digest.patch`.** Finney's runtime advertises both `AuraApi` and `BabeApi`, while its blocks are authored with Aura only, so upstream smoldot refuses the chain (`MultipleConsensusAlgorithms`). When the block it starts from isn't the genesis, the patch lets that block's header decide: exactly one Aura or BABE pre-runtime digest selects that engine. A header with neither or both keeps upstream's refusal.
2. **`0002-bootstrap-from-database-without-light-sync-state.patch`.** Upstream smoldot starts anywhere but the genesis only from a BABE chain spec's `lightSyncState`. Subtensor's spec has an Aura checkpoint instead (`grandpaWarpSyncCheckpoint`), and a warp sync from the genesis stops at a forced GRANDPA change. The patch takes the chain information from a database whose genesis hash matches the chain spec (upstream already checks that). As smoldot documents for `databaseContent`, the database is trusted input. Here it is `../src/finney-checkpoint.json`, which `../scripts/finney-checkpoint.py` makes from the spec, and afterwards the state the light client verified and saved itself.
3. **`0003-ruzstd-0.9.1-for-rustsec-2026-0344.patch`.** smoldot 3.7.0 locks `ruzstd` 0.8.2, which [RUSTSEC-2026-0344](https://rustsec.org/advisories/RUSTSEC-2026-0344.html) covers: a crafted zstd input under 128 KB makes it allocate gigabytes. smoldot uses it to decompress runtime code. That code arrives with storage proofs, but the proof may be against a best block that only its Aura author signed. The patch moves to 0.9.1, which fixes it, with no change to smoldot's code; smoldot's own zstd tests pass with it.

A Durable Object's isolate has 128 MB, and V8 counts a Wasm memory in steps: 32 MiB, then 64, then 128 (measured in Wrangler's local runtime with `--trace-gc-verbose`). Wasm memory never shrinks, so what counts is smoldot's highest point. Unpatched, a restart from a saved state took it to 57 MiB and the first metadata request to 75 MiB, which V8 counts as 128 MiB: Cloudflare reset the object. smoldot itself reported 18 to 36 MiB in use; the rest came from transient peaks, one patch each:

4. **`0004-reuse-the-warp-synced-runtime.patch`.** The runtime that warp sync hands over isn't registered among smoldot's compiled runtimes. So the first JSON-RPC runtime call (`state_call`, `state_getMetadata`) compiles an identical second copy: a 16 MiB decompression and a second module. Registering it makes that call reuse it. On its own, this kept the Bittensor calls below at 40.5 MiB instead of 75.5.
5. **`0005-zstd-decode-in-steps-into-an-exact-buffer.patch`.** Finney's runtime is 2.6 MiB compressed and 10.4 MiB decompressed, and its zstd frame doesn't say so. Decoding the frame at once grew the decoder's buffer by doubling to 16 MiB, then copied it out. The patch decodes in 1 MiB steps, the decoder keeping only its 2 MiB window, once to count and once into a buffer of exactly the output's size. A restart from a saved state then peaked at 37.9 MiB instead of 57. A new test checks the output against decoding the frame at once, and the size limit at its exact boundary.
6. **`0006-database-leaves-out-code-too-large-to-fit.patch`.** Saving the verified state (`chainHead_unstable_finalizedDatabase`) encoded the runtime's code in base64 into the database, serialised all of it, found it over the size asked for and only then left the code out: 7 MiB at once, every save. The code is now left out first when its encoding alone can't fit.
7. **`0007-legacy-runtime-calls-use-pinned-runtimes.patch`.** For every block a legacy runtime call names, smoldot downloaded the block's `:code` from a peer (2.6 MiB in a proof) and compared it with its compiled runtimes, although its runtime service already holds the runtime of recent blocks. The call now takes it from there, as `chainHead_v1_call` does, and downloads only for blocks the service doesn't hold. The first metadata request went from about 3 s to 0.5–0.7 s.

8. **`0008-compile-the-runtime-once-from-a-stream.patch`.** Even decompressed into an exact buffer, the 10.4 MiB runtime was held whole while wasmi copied its code, and smoldot built it twice: a strict build failed on Finney's import of a BLS12-381 host function that smoldot lacks, and a second build allowed it. Now a compressed runtime that the interpreter compiles lazily (the light client's case) is decompressed twice as a stream, never whole: once to keep just its `runtime_version` and `runtime_apis` sections, then straight into wasmi's streaming parser, which holds one function at a time. It is built once, allowing unresolved imports, with the same warning about the first one (`HostVmPrototype::unresolved_imports`). wasmi now ignores custom sections, which smoldot reads itself, sparing the runtime's 1 MiB of debug names. A restart from a saved state, in the order Cloudflare runs it, then peaked at 25.2 MiB instead of 32.6–32.8. New tests check that the streamed runtime has the same version and gives byte-identical `Core_version` and `Metadata_metadata`, that the two sections read from a stream match those of the whole module, and that the reader fails past its limit and on invalid data.

With all eight, measured the same way (24 October 2026, live Finney): 25.2 MiB after a restart from a saved state, then 37.6 MiB after the metadata, a subnet's neurons, all subnets' dynamic info and 22 calls at once. V8 counts the latter as 64 MiB: its count of memory outside its heap peaked at 76.5 MiB, or about 111 MiB with smoldot's code compiled up front. Most of what a runtime call adds is the runtime's own memory (4.2 MiB for the metadata, in a buffer that doubles as it grows) and its translated code, which wasmi keeps. smoldot's own tests pass (495 in `smoldot`, 82 in `smoldot-light`), and `../scripts/check.mjs` found every answer identical to a full node's.

The first two are the same changes [Umi-BitSign](https://github.com/Umi-BitSign/umi) makes to smoldot 2.2.0 and smoldot-light 1.3.2 for its GRANDPA finality observer (`rust/grandpa-finality-observer/vendor/PATCHES.md`), where it also pins `ruzstd` 0.9.1. Here they are written for 3.7.0.

## Rebuilding

```sh
sh smoldot/build.sh
```

The script clones the tag, checks the commit and applies the eight patches. It then builds with the settings of smoldot's npm package (`--profile min-size-release` for `wasm32-unknown-unknown`, no default features), with local paths remapped so the file contains none of the computer's. It needs git and Rust with the `wasm32-unknown-unknown` target, and takes about a minute once the crates are downloaded.

Built with rustc 1.93.1 (01f6ddf75 2026-02-11) on Linux (aarch64) on 24 October 2026, two builds from fresh clones were byte-identical: 5,561,372 bytes, sha256 `47f5b214d7dff29d6762b5270421187bd814a596b3b5ae524650458bc3bb44f9`. Another Rust version, or another host, builds a working file with a different hash: with the first three patches, macOS built 5,530,407 bytes (sha256 `5591b0fc…622e`) where Linux built 5,530,372.
