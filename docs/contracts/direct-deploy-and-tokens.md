# Contract: API tokens, CLI login, direct uploads, MCP

Shared by four features: API tokens (A), direct uploads and drag-and-drop (B), the `shipcel` CLI (C), and the MCP server for AI agents (D). All four are implemented; keep these HTTP shapes exactly, because the CLI, the dashboard and the MCP server all depend on them.

Every app still runs in the **user's own Cloudflare account** (no anonymous hosting): direct uploads use the workspace's Cloudflare connection, like Manage operations.

## 1. Bearer tokens (A)

- Format: `cc_pat_` followed by 43 base64url characters (32 random bytes). Stored only as `SHA-256` hex (`digest()` in `worker/crypto.ts`), with a display prefix of the first 12 characters.
- Migration `0018_api_tokens.sql`: `api_tokens(id TEXT PRIMARY KEY, workspace_id TEXT NOT NULL, user_id TEXT NOT NULL, name TEXT NOT NULL, token_hash TEXT NOT NULL UNIQUE, prefix TEXT NOT NULL, created_at INTEGER NOT NULL, last_used_at INTEGER, expires_at INTEGER, revoked_at INTEGER)`; device-login table `cli_logins(...)` in the same migration.
- `Authorization: Bearer cc_pat_…` authenticates `/api/*` and `/mcp`. The identity is the token's user and workspace, with the role from `memberships` (re-checked on every request); `sessionHash` is `pat:<token id>`. A request with a Bearer token ignores cookies, needs no `Origin`/`X-Shipcel-Request` check (no ambient credentials), and is refused if the token is unknown, revoked, expired, or its membership is gone (401, `{"error": "…"}`).
- Bearer requests may **not**: create, list or revoke tokens; approve or look up CLI logins; start or finish OAuth (`/api/auth/*`); change connections (`/api/connections/*` writes); turn Free-only on or off (a billing decision). Everything else (projects, deployments, Manage operations, uploads, backend) works as with a session. Implemented in `worker/tokens.ts`.
- Routes (session cookie, workspace owner):
  - `GET /api/tokens` → `[{ id, name, prefix, createdAt, lastUsedAt, expiresAt }]` (seconds since epoch; never the token).
  - `POST /api/tokens` `{ name, expiresInDays?: 1..365 }` → `201 { id, name, prefix, token, createdAt, expiresAt }`; `token` is returned once.
  - `DELETE /api/tokens/:id` → `{ revoked: true }`.

## 2. CLI login: device authorization (A)

1. `POST /api/cli/login` `{ host? }` (no auth; send `X-Shipcel-Request: 1`) → `201 { code: "ABCD-EFGH", deviceSecret, verificationUrl: "<origin>/app/#cli-login?code=ABCD-EFGH", expiresIn: 600, interval: 2 }`. Store only hashes of `deviceSecret`; `code` is 8 characters from an unambiguous alphabet. Rate-limited.
2. The user opens `verificationUrl`, sees the code, and approves: `POST /api/cli/login/approve` `{ code }` (session cookie, owner or developer) → `{ approved: true }`, or `POST /api/cli/login/deny` `{ code }`. The page reads `GET /api/cli/login/:code` → `{ code, host, status, createdAt, expiresAt, mine }` (`mine`: this person decided it, in this workspace; who decided it is never returned). A browser that isn't signed in signs in from that page and comes back to it: `GET /api/auth/github/start?return=cli-login:<code>` (and `/api/auth/cloudflare/start?return=…` to connect Cloudflare) keep `return` with the OAuth state, and the callback redirects to `/app/?connection=success|declined#cli-login?code=<code>`. `return` is `cli-login:<code>` or `cli-setup` (the page at `/app/#cli-setup`, which only connects Cloudflare); anything else goes back to Connections.
3. The CLI polls `POST /api/cli/login/poll` `{ deviceSecret }` (with `X-Shipcel-Request: 1`) → `202 { status: "pending" }`, `200 { token, workspace }` exactly once after approval (a new token named `CLI on <host>`; later polls → 410), `403 { status: "denied" }`, or `410 { status: "expired" }`.
4. With its token the CLI reads `GET /api/me` → `{ login, workspace, workspaceName, role, via }` and `GET /api/connections`; while Cloudflare isn't connected with an account, it waits (in a terminal) for the person to finish on the page, asking `GET /api/connections` every two seconds. Tokens can't change connections: that stays in the browser.

## 3. Direct uploads (B) — used by drag-and-drop, the CLI and MCP

Static files (and optionally one Worker module) are uploaded to a project and deployed as a Worker with static assets in the project's Cloudflare account. A project's first upload creates its Worker; later uploads create new versions of the same Worker. Implemented in `worker/uploads.ts`; hashing and limits in `shared/assets.ts`.

- Asset hash (Cloudflare's, as Wrangler 4.148 computes it): `blake3(base64(fileBytes) + extension).hex().slice(0, 32)`, where `extension` is the file extension without the dot (`""` if none). Use `assetHash()` from `shared/assets.ts` (`@noble/hashes/blake3.js`). The server recomputes it for every received file and refuses mismatches.
- Paths start with `/`, use `/` separators, no `.`/`..`/empty segments, no hidden files except under `/.well-known`; at most 20,000 files (Cloudflare's Free-plan limit) and 24 MiB per file through Shipcel (Cloudflare allows 25 MiB). `/_worker.js`, `/_redirects` and `/_headers` configure the deployment and are refused as files: send them with the deploy request.
- `POST /api/projects/:id/uploads` `{ files: [{ path, hash, size }], workerName? }` → `201 { uploadId, workerName, missing: [hash, …], buckets: [[hash, …], …], maxRequestBytes, expiresAt }`. `missing` lists the hashes Cloudflare still needs (grouped into `buckets` as Cloudflare suggests). `workerName` applies only to a project's first upload (default: the project name); an existing Worker with that name is never adopted.
- `POST /api/projects/:id/uploads/:uploadId/files` `{ files: [{ hash, content /* base64 */ }] }` (each request ≤ `maxRequestBytes`; send a bucket per request) → `{ received, missing: [hash, …] }`.
- `POST /api/projects/:id/uploads/:uploadId/deploy` `{ requestId: uuid, confirm: true, publish?, spa?, workerModule? /* base64 ES module, ≤ 1 MiB */, redirects? /* _redirects text */, headers? /* _headers text */ }` → journaled like other Manage changes: `200 { id, status: "succeeded", result: { workerName, versionId, previewUrl, url, published } }` or `502 { status: "needs_attention", error }`. A project's first upload stays unpublished unless `publish: true`: its workers.dev route is off and only its version preview address (`https://<first 8 of version id><preview_url_suffix>`) works. Later uploads keep the current published state unless `publish` is given. Without `workerModule` the Worker serves only files (no code runs); `spa` sends unknown paths to `/index.html`; a `/404.html` file is used for unknown paths.
- `POST /api/projects/:id/publish` `{ requestId, confirm: true }` → turns the route on; `POST /api/projects/:id/unpublish` likewise turns it off.
- `GET /api/projects/:id/uploads` → `[{ id, status, files, bytes, createdAt, versionId, url, previewUrl, published }]` (newest first, at most 30).
- A project that deploys from Git refuses direct uploads (409); a project with direct uploads can't start a Git pipeline or branch previews (409). Free-only projects can use direct uploads: they create only Workers and static assets.
- Rollback for any project: the existing `GET /api/projects/:id/versions` and `POST /api/projects/:id/rollback` `{ requestId, confirm: true, versionId }`.

## 3b. Deploys of apps with code and bindings, from a computer

Used by the shipcel CLI for a folder with a Wrangler configuration. Wrangler runs on the person's computer; for one deploy it reaches Cloudflare through Shipcel. Session routes take a browser session or an API token; Wrangler's own calls take the session's token.

- `POST /api/local-plan` `{ files }` → `{ framework, adapter, buildCommand, resources, warnings, issues, workerName? }`. `files` maps the root files a review reads (`package.json`, `wrangler.json(c)`, `open-next.config.ts`, `next.config.{ts,mjs,js}`, `pyproject.toml`, lockfiles, Vite and Astro configs) to their contents, `"present"`, or `null`; any other name is refused. `package-lock.json` is reduced to `{ packages: { "node_modules/next": { version }, … } }`. The review is the GitHub one (`worker/repository-plan.ts`) without what only Cloudflare's builds need (npm and a committed lockfile, no workspaces).
- `POST /api/projects/:id/local-plan` `{ files, workerName?, production? }` → the same plus `workerName`, `first`, `production` and `create: [{ type, binding, name }]` (what Cloudflare creates now; resources named `<worker>-<binding>`). Problems the person can fix are `issues`; a project that deploys from GitHub answers 409.
- `POST /api/projects/:id/local-deploys` `{ requestId, confirm: true, files, workerName?, production?, confirmResources? }` → 201 `{ id, token, apiPath, accountId, workerName, adapter, production, first, expiresAt }`. 409 with the issues joined; 400 `{ error, create }` when resources would be created and `confirmResources` isn't true; 409 while another deploy of the project is active (a session unused for two minutes is closed and taken over). A new app's first deploy is production whatever `production` says. Journaled as `local.deploy` or `local.preview`. The token is shown once, stored as a hash, and good for this session only. A session ends when it is finished or its hour is up, when the person who opened it is no longer a developer of the workspace, when the workspace's Cloudflare connection changes, and when the sign-in that opened it ends (an API token revoked or expired, a browser session signed out or run out). Opening a deploy closes the workspace's sessions whose hour is up, each with its operation and with Cloudflare's sealed upload tokens.
- `ALL /api/wrangler/:id/client/v4/*` with `Authorization: Bearer <token>`: Cloudflare's API as Wrangler calls it (`CLOUDFLARE_API_BASE_URL`), answered in Cloudflare's envelope. Allowed: reads of the session's own Worker (`services`, `workers`, `secrets` names, `script-settings`, `subdomain`, `schedules`; `deployments` reduced to each deployment's id, source, strategy, date and versions; `settings` with bindings reduced to name and type; a version's details are not readable, since they carry variable values); the account's `workers/subdomain`; empty lists for D1, KV and R2; the assets upload session and file upload (Cloudflare's tokens are kept sealed and replaced by the session's token, also when Cloudflare refuses); creating the D1, KV and R2 resources the person agreed to, by their expected names; the script upload (`PUT`) and version upload (`POST …/versions`), whose metadata must pass `worker/wrangler-policy.ts` and which go on with only the `excludeScript`, `bindings_inherit` and `include_subdomain_availability` flags; and for production sessions only `POST …/deployments` (the uploaded version at 100%), `PATCH …/script-settings` (tags, and observability as on or off, sampling and persistence, never destinations), `POST …/subdomain` and `PUT …/schedules` (five at most). Anything else answers 403.
  - Every request other than `GET` and `HEAD` declares its `Content-Length` (411 otherwise, also for a chunked body), and is sized by it before the token is checked or any of it is read: 100 MB for a batch of files (streamed to Cloudflare), 32 MB for the app's code, 8 MB for the list of files, 64 KB for anything else (413). An upload has at most 2,000 parts.
  - A new app's Worker doesn't exist until the session's own `PUT` creates it: until then version uploads, deployments, settings, the address and schedules answer 409, and the `PUT` answers 409 if a Worker of that name has appeared. For an app that exists, an upload answers 409 when the Worker's tag is no longer the one that was reviewed.
  - A session makes at most 240 calls a minute and a workspace's sessions 600 (429). Calls without the session's token count towards neither.
  - Every answer, including failures inside Shipcel, is in Cloudflare's envelope; a refusal's message starts `Shipcel:`.
- `POST /api/projects/:id/local-deploys/:deployId/finish` `{ failed? }` → `{ result: { workerName, versionId, previewUrl, url, published, preview, productionUrl, created } }`, the same shape as an upload's deploy plus the resources created. 409 with what the deploy left when it didn't finish: nothing, the resources it created, a version production doesn't serve yet, or a version that was deployed by a session that had already been closed. Idempotent once deployed.

## 4. MCP (D)

Implemented in `worker/mcp.ts`, mounted in `worker/index.ts`; tests in `tests/mcp.test.ts`.

- Endpoint `POST /mcp` on Shipcel's own origin (`APP_ORIGIN`), Streamable HTTP with JSON responses only (no SSE, no sessions); `GET`/`DELETE` → 405 with `Allow: POST`. `wrangler.jsonc` lists `/mcp` in `run_worker_first`. Requests are limited to 10 MiB (413), because files travel inline as JSON and the Worker has 128 MB of memory.
- Authentication: `Authorization: Bearer cc_pat_…` only (cookies are ignored) → otherwise 401 with `WWW-Authenticate: Bearer realm="shipcel", error="invalid_token"`. A present `Origin` other than Shipcel's own → 403. No OAuth yet, so connectors that only sign in with OAuth (chat apps' connector settings) can't connect.
- Protocol revisions: **2026-07-28** (stateless: every request carries `_meta["io.modelcontextprotocol/protocolVersion"]` and `_meta["io.modelcontextprotocol/clientCapabilities"]`, and the `MCP-Protocol-Version`, `Mcp-Method` and, for `tools/call`/`prompts/get`/`resources/read`, `Mcp-Name` headers, which may be `=?base64?…?=`-encoded; mismatches → `-32020` (400); unsupported version → `-32022` (400) with `data: { supported, requested }`; missing `_meta` keys → `-32602` (400); unknown methods → `-32601` (404); every result has `resultType: "complete"` and `_meta["io.modelcontextprotocol/serverInfo"]`) and **2025-11-25, 2025-06-18, 2025-03-26** (`initialize` negotiates the version, `notifications/*` → 202, an unsupported `MCP-Protocol-Version` header → 400). `server/discover` returns `supportedVersions`, `capabilities: { tools, prompts }` and `instructions`; `ping` works in both.
- Tools call the HTTP API above internally (`app.fetch` to `<APP_ORIGIN>/api/…` with the same token), so permissions, rate limits and journaling are identical; changes send `{ requestId: <new UUID>, confirm: true }`. Tools: `list_projects`, `create_project` (`framework` defaults to `static`; projects are Free-only by default), `get_project`, `deploy_files` (`files: [{ path, content, encoding?: "utf8" | "base64" }]`, `publish?`, `spa?`, `app_name?`; `/_worker.js`, `/_redirects` and `/_headers` go to the deploy request; the server hashes the rest and uploads only what Cloudflare lacks), `publish` (`public: boolean`), `list_deployments`, `list_versions`, `rollback` (`version_id?`, default the version before the one serving 100%), `list_secrets` (names only), `set_secret` (the value is never echoed), `get_signin_info`. API refusals become tool results with `isError: true` and the API's message; unknown tools → `-32602`; unexpected failures → `-32603` (500).
- Prompt `build_and_deploy` (`idea`): asks the agent to build within what direct uploads support, deploy, show the preview, and ask before publishing.

## 5. Distributing the CLI

The `shipcel` package is not on the npm registry (the name was unregistered on 8 Oct 2026; publishing it is the owner's decision). `npm run cli:build` bundles `packages/cli/src` into `packages/cli/dist/shipcel.js` and packs it, laid out like `npm pack` with fixed times, as `public/cli/shipcel.tgz` (both gitignored build output; `npm run build` and `npm run dev` run it first). Every Shipcel therefore serves its own CLI: `npm install -g <origin>/cli/shipcel.tgz`, or in CI `npx --yes --package=<origin>/cli/shipcel.tgz shipcel deploy …`. The dashboard's API & CLI page shows these commands with its own origin.
