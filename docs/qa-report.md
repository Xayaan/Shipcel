## What this does not establish

Nothing from 13 October 2026 has run live: the session ran in a VM, and the owner's Cloudcel, with their GitHub and Cloudflare connections, runs on their own computer. Still to be seen with real providers: the sign-in round trip that returns to the CLI's page (GitHub's and Cloudflare's redirects with the stored return target), a real framework build uploaded by `cloudcel` (the upload path itself ran live on 9 October), and every wait in `cloudcel git connect`, including whether Cloudflare's repository check turns positive once its GitHub app is connected (`--skip-checks` exists because that is unconfirmed).

No repository build through Workers Builds, build-token registration through the Builds API, resource provisioning during a build, push-triggered redeploy, hosted cron run, preview alias, container image push or rollout, D1 export, or point-in-time restore has been tested live. Native resource creation stays disabled until the dedicated-account steps in `provider-setup.md` succeed. Browser/provider fixtures and dry runs must never be described as real hosted deployments.

Dry runs prove configuration, bundling, binding declarations, and (for containers) local image builds only. Unverified in Workers Builds: creation and reuse of draft D1/R2/KV resources with a customer build token, the Astro session/Images defaults, SvelteKit 3's Node.js 22.17 requirement, Python and pipx in the build image, Docker builds and image pushes, the build-token permission containers need, first-container provisioning time, and branch alias URLs. Containers require the Workers Paid plan, which Cloudcel cannot detect; a Free account's build fails.

GitHub adapters require trusted repositories: apps commit Wrangler JSON/JSONC, and static sites get a configuration Cloudcel writes during the build; Cloudcel does not run framework automatic configuration or rewrite repositories. Runtime secrets, version promotion and rollback ran live for a direct-upload app on 9 October 2026. Domain attach/detach, backups, branch previews of GitHub projects, and sign-in & realtime are implemented with fixture evidence (the service itself also runs in workerd locally) and have not been verified against live provider responses or real browsers' passkey prompts. Cloudcel does not implement email/password sign-in, row-level security, data APIs, scheduled exports run by Cloudcel itself, or WordPress hosting, and no GitHub import adapter has been verified live.

Timeouts and uncertain resource mutations stop with `needs_attention`; owners reconcile them with **Check Cloudflare**. Local disconnect erases credentials and stops pending Cloudcel operations while native apps/triggers remain. Upstream grant revocation and transparent key rotation remain production work.

Public hosting requires `AUTH_MODE=github`, exact HTTPS `APP_ORIGIN`, remote D1, and secrets. The dev server remains loopback-only. GitHub CI configuration exists locally, but no remote repository or hosted CI run has been created. Field performance and production cost have not been measured. Migrations 0001–0015 are applied to local D1; test projects were cleaned up. The D1 HTTP API's atomicity for a multi-statement migration is undocumented; the restore point is the guaranteed recovery path. Recovery, health tracking, previews, and backups rely on Workers Builds, deployments, and D1 response fields taken from Cloudflare's API reference, not from live responses. Health checks probe only the workers.dev homepage: apps that disable workers.dev, require authentication, or redirect their homepage report as unhealthy.
