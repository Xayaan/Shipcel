Every locally verified kit uses Wrangler 4.148.0 and compatibility date 2026-10-07. Independent npm installs, builds, Worker dry-run bundling, and a local run of each app in Wrangler (pywrangler for Python) answering `/` and `/api/health` are recorded in `starter-kit-verification.json`. No adapter has been tested with a live deployment in a customer account yet.

For every new adapter record: adapter version, framework versions, runtime, services, feature restrictions, test fixture, local build evidence, live deployment evidence, and last verification date. A failed verification must downgrade the exposed capability rather than leave a misleading “supported” status.

Resource/service roadmap: Queues and Workflows will be added as adapter capabilities. Hyperdrive (Postgres and MySQL hosted elsewhere) is supported since 28 October 2026: a `hyperdrive` entry is accepted only for a configuration Shipcel added to the same project (`worker/hyperdrive.ts`), and nothing is created for it on deploy. Draft D1, R2, and KV bindings (binding name only, no IDs) are created by Wrangler during a reviewed native deployment; this is dry-run and fixture evidence only. Durable Object bindings are accepted only in container repositories, and only for classes of the same Worker. D1 migrations are reviewed and applied from Manage → Database (Wrangler-compatible `d1_migrations` tracking, a Time Travel restore point first, and a confirmed restore action); they are never applied automatically.

Backups: Manage → Database exports a database on demand to a one-hour download link and restores it to any time in Time Travel's window (7 days on Workers Free, 30 days on Workers Paid; restores are confirmed and return an undo bookmark). Cloudflare blocks queries while an export runs, so Shipcel never schedules exports itself; starter kits with a database include an optional GitHub Actions export workflow the owner can schedule. Secrets never belong in the shared catalog, browser state, or exported project plans.

Every adapter also accepts these settings of Cloudflare's free platform in the Wrangler configuration (`inspectPlatform` in `worker/repository-plan.ts`): `ai`, `browser`, `images` and `version_metadata` bindings with only a binding name; `vars` with plain text, number or true/false values; `placement` with only `mode: "smart"`; `triggers.crons` with up to five five-field cron expressions (Cloudflare allows 5 per account on the free plan); and, outside the container adapter (which reviews its own), Durable Objects of the app's own Worker: `durable_objects.bindings` without `script_name`, and `migrations` that only create (`new_sqlite_classes`), rename or delete classes. Key-value Durable Objects (`new_classes`, Workers Paid) and transfers between Workers are refused, every bound class needs a migration that creates it, and binding names stay unique across all kinds. Queues and Workflows are not accepted yet: their names are account-wide, and Shipcel never adopts an existing resource. `tests/deploy-command.test.ts` runs a production dry run with these settings against Wrangler 4.148.0. Cron schedules can also be set in Manage → Schedules (`GET`/`PUT /api/projects/:id/schedules`, journaled `schedules.set`, recoverable with Check Cloudflare); a configuration that lists `triggers.crons` replaces them on each deploy, because Wrangler only writes schedules when the configuration declares them.

Branch previews use Cloudflare's Worker Previews (open beta since 22 September 2026). After production is deployed, an owner turns previews on: Shipcel creates staging copies of the app's D1 databases, KV namespaces and R2 buckets (`<worker>-pv-<suffix>-<binding>`, after consent; Free-only refuses R2), asks the repository to commit the `previews` block it generates (Wrangler fails every preview build without one, and Previews inherit no bindings), checks that the block binds exactly those copies, then adds a second trigger on the production Worker that runs `npx wrangler@4.148.0 preview --worker-name <worker>` for every branch except the production branch, and turns on workers.dev Preview addresses. Each branch becomes a Preview named after it (`<branch>-<worker>.<subdomain>.workers.dev`); Workers Builds comments the address on pull requests. All branches share the staging copies. Previews can be listed (address, latest deployment, commit, pull request) and deleted; turning previews off deletes only the preview trigger. Refused for Next.js (service bindings from a Preview reach production, and OpenNext calls itself through one), containers (per-Preview container applications are partly supported and unverified) and Python Workers with packages (pywrangler with Previews is unverified). The design and its open questions are in `docs/research/workers-previews.md`.

## WordPress proof checklist

Where the experimental kit stands (29 Oct 2026): the design answers every item below except backups; none of them has been proven yet.

- Choose MySQL/MariaDB provider, ownership, pricing, backup policy, and connection path. (Kit: any MySQL 8 or MariaDB 10.6+ the customer owns, over TLS from the container; no Hyperdrive, which serves Workers, not containers.)
- Choose durable upload storage with WordPress-compatible semantics.
- Persist plugins/themes by a tested storage or reproducible-image strategy.
- Verify admin/editor, uploads, scheduled tasks, email, domains, cache, and updates.
- Restart and replace a container after uploads/plugin installation; verify all expected state remains.
- Restore a database and media backup into a separate fresh environment.
- Test important plugin combinations independently; do not promise arbitrary plugin compatibility.

The deploy command is `npx wrangler@4.148.0 deploy --no-autoconfig --x-provision --x-auto-create --name <Worker name>`, where the Worker name is the app name the owner chose (default: the project name; it is also the free `<name>.<subdomain>.workers.dev` address), or the configured name for Next.js and containers; a unit test runs it against the installed Wrangler with `--dry-run`. `--name` matches the connected Worker that Workers Builds expects, so the repository's own configuration name never triggers Cloudflare's name-mismatch pull request. Wrangler names created resources `<Worker>-<binding>`, so Shipcel shortens the generated Worker name when R2 bindings are present to keep bucket names within 63 characters; Next.js and containers keep their configured name (OpenNext's self-reference, and Wrangler names container applications after the configured name even when `--name` differs), and Shipcel rejects chosen or configured names whose bucket names would exceed the limit. Worker names are unique per Cloudflare account (migration 0009), never adopted: the first pipeline step stops if the name already exists. Wrangler 4.148 always requests a new resource named `<Worker>-<binding>` and never adopts an existing one, so a name that is already taken in the account makes the build fail rather than reuse that resource. Existing resource IDs, names, routes, and environments are rejected rather than adopted; containers are accepted only by the container adapter. After the initial build Shipcel reads the Worker's bindings, records the created resource IDs, and refuses to publish a URL if a reviewed binding is missing or an unreviewed D1/R2/KV/Queue/Vectorize/Hyperdrive binding appears.

OAuth, job authorization, failures, idempotency, leases, and health-checked success have fixture tests. Live provider compatibility and deployment are **unverified** and disabled by default. Account registration, Cloudflare's own GitHub integration, and a native build token are required. See `provider-setup.md`. Native auto-deploy delegates future builds/history and billing to Cloudflare; it is not a full Vercel/Supabase feature set.
