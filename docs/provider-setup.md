# Activate Shipcel account connections and native deployments

Status: implementation and fixture tests pass locally. No live provider consent or cloud deployment has been verified. Keep native deployments disabled until the dedicated-account checks below pass. Do not send credentials in chat or commit them.

## 1. Local configuration

`npm run dev` creates `.dev.vars` (ignored by Git) from `.dev.vars.example` with a fresh `TOKEN_ENCRYPTION_KEY` (32 random bytes as 64 hex characters) when the file doesn't exist; it never changes an existing file. Keep the key in a password manager as well: losing it means setting up sign-in and reconnecting accounts again.

**Local sign-in setup from Connections (local mode only).** A local Shipcel (loopback, `AUTH_MODE=local`) sets up its own GitHub App and Cloudflare OAuth client from the Connections page, so nothing has to be registered by hand or pasted into `.dev.vars`:

- **GitHub:** _Create GitHub App on GitHub_ posts an app manifest to GitHub (personal account or an organization): a private app named `Shipcel <random>`, homepage `APP_ORIGIN`, callback `APP_ORIGIN/api/auth/github/callback`, Contents and Workflows read and write (to add the deploy workflow) and Metadata read, no webhook. You check it and click _Create GitHub App_; GitHub returns to `APP_ORIGIN/api/setup/github/created`, and Shipcel exchanges the one-hour code (`POST /app-manifests/{code}/conversions`) for the client ID and secret, stored encrypted. The private key and webhook secret aren't kept. The browser that started must finish (state cookie, single use, one hour).
- **Cloudflare:** create a temporary API token (Create Token → Custom token) with one permission, _Account · OAuth Client · Edit_, and paste it. Shipcel lists the accounts it can see and Cloudflare's scope list (`GET /client/v4/oauth/scopes`, IDs like `account.read`), matches the permissions it uses by name or ID, shows them, and on confirmation creates a private client (`POST /accounts/{id}/oauth_clients`: `client_secret_post`, `authorization_code` and `refresh_token`, response type `code`, redirect `APP_ORIGIN/api/auth/cloudflare/callback`, the matched scopes plus `offline_access`, retried without it if Cloudflare refuses that scope). Only the client ID and encrypted secret are stored; the token is used for those calls only. Delete it in Cloudflare afterwards. Or create the client by hand and paste its ID, secret and scope IDs.

Values in `.dev.vars` take precedence over this setup. A hosted Shipcel never offers it: configure sections 2–3 in its environment. **Live-checked on 8 Oct 2026** with a real GitHub account and a real Cloudflare account: the manifest flow created the GitHub App with loopback URLs and GitHub sign-in completed; Cloudflare's client API accepted the loopback redirect, listed scope IDs such as `account-settings.read`, `workers-scripts.write`, `workers-ci.write`, `workers-r2.write`, `access.write` and `access-acct.write`, accepted `offline_access`, and the Cloudflare sign-in completed. Choosing the account, a token refresh, reading the workers.dev subdomain and listing build tokens through the Builds API then worked with the OAuth token. **Found live:** that first client was registered with `workers-scripts.edit`, which Cloudflare's scope list names _Workers Editor_: it updates existing Workers but can't create one, so Cloudflare refused the first upload's `assets-upload-session` with "No access to the specified resource." Shipcel now asks for `workers-scripts.write` (_Workers Scripts Write_) and never falls back to Workers Editor; Connections offers **Update Cloudflare sign-in** for a client set up before the fix, and deploys that would create a Worker say so before calling Cloudflare.

Run `npm run setup:check` to validate configuration names without printing their values. Restart the dev server after changing `.dev.vars`.

`AUTH_MODE=local` permits the offline, loopback-only workspace. GitHub sign-in creates a separate personal workspace; local plans remain in the offline workspace. For hosted operation, set `AUTH_MODE=github` and `APP_ORIGIN` to the exact HTTPS origin, with no trailing slash. The API rejects another origin and public unauthenticated mode.

The public URL/domain, GitHub App registration, and Cloudflare OAuth client registration are owner-provided configuration. None has been created by this implementation.

## 2. Register the GitHub App

Create a GitHub App owned by your company/account. Request repository **Contents: read and write**, **Workflows: read and write** and **Metadata: read**: Shipcel adds its deploy workflow (`.github/workflows/shipcel.yml`) to a repository when someone connects it and confirms, and writes nothing else. Install it on selected repositories; the signed-in user must independently have push/admin access to connect them. An app created before 23 Oct 2026 asked for Contents read only: on GitHub, open the app's settings → **Permissions & events**, set Contents and Workflows to read and write, save, and accept the new permissions on each installation (the installation's page shows a request to review).

Set the user authorization callback to `APP_ORIGIN/api/auth/github/callback`. Use the actual origin, not the literal placeholder. Fill `GITHUB_CLIENT_ID`, `GITHUB_CLIENT_SECRET`, and `GITHUB_APP_SLUG`. User access token expiration/refresh is supported. Enable the App's OAuth user authorization flow. Webhooks are not used: GitHub Actions runs the deploy workflow on every push (or Cloudflare's own builds do, for a project set up that way).

Set the **Setup URL** to `APP_ORIGIN/api/auth/github/installed` and turn on **Redirect on update**. Leave **Request user authorization (OAuth) during installation** off: Shipcel signs people in with state and PKCE, which that option skips. Apps that Shipcel creates from a manifest (Connections, `npm run production:setup`) have all of this already.

In Shipcel → Connections, **Connect GitHub** signs you in. Someone whose GitHub hasn't installed the app goes on to GitHub's page for choosing repositories, and the Setup URL brings them back to where they started. **Change repositories** opens that page again later. Both the user's access and the App's installation constrain repository results.

See [GitHub App user authorization](https://docs.github.com/en/apps/creating-github-apps/authenticating-with-a-github-app/authorizing-users-during-installation) and [generating a user access token](https://docs.github.com/en/apps/creating-github-apps/authenticating-with-a-github-app/generating-a-user-access-token-for-a-github-app).

## 3. Register the Cloudflare OAuth client

Follow [Cloudflare client registration](https://developers.cloudflare.com/fundamentals/oauth/create-an-oauth-client/) and [OAuth integration](https://developers.cloudflare.com/fundamentals/oauth/integrate-with-cloudflare/). Register your verified application domain and exact `APP_ORIGIN/api/auth/cloudflare/callback` redirect. This server uses authorization code + PKCE S256 and confidential-client authentication with `client_secret_post`; configure the client accordingly.

Set `CLOUDFLARE_CLIENT_ID`, `CLOUDFLARE_CLIENT_SECRET`, and `CLOUDFLARE_OAUTH_SCOPES`. Obtain real scope names from the authenticated `/client/v4/oauth/scopes` endpoint and the client registration interface. Select the minimum scopes for account discovery, Workers Scripts Write (`workers-scripts.write`: not _Workers Editor_, `workers-scripts.edit`, which can't create Workers), and Workers Builds configuration. Manage → Database additionally needs D1 read/write, including Time Travel bookmark and restore and database export. Free addresses need read access to the account's workers.dev subdomain and, to let owners claim one, permission to register it. Do not invent scope strings or substitute API-token permission labels for OAuth scopes. If Builds permissions are unavailable for your client, stop here and retain manual kit deployment.

Sign in through GitHub first. Then connect Cloudflare, load authorized accounts, and explicitly choose the deployment account. The callback is bound to the same user, workspace, and session that started it. Tokens stay encrypted on the server; only connection metadata is sent to the browser.

## 4. Cloudflare native Builds prerequisite and compatibility gate

The [Builds API guide](https://developers.cloudflare.com/workers/ci-cd/builds/api-reference/) documents user-scoped API authentication, a separate build-token UUID, and a one-time Cloudflare GitHub App installation. Its applicability to a third-party OAuth grant must be verified with your actual client before enabling this adapter.

In a dedicated Cloudflare test account, authorize Cloudflare's GitHub integration through a Worker's Settings → Builds → Connect. Set up a build token with the minimum permissions needed for that test Worker. Shipcel lists token names and UUIDs, never token values.

With the connected OAuth account, open Connections: the build tokens load by themselves (this must succeed with the real OAuth grant), and the GitHub card asks Cloudflare whether its GitHub app can read your repositories (`GET /accounts/{id}/builds/repos/github/{owner}/{repo}/config_autofill?branch=…`, Workers CI read; Cloudflare answers 404, code 12000, for a repository it can't read). Connect the app through the dashboard (Create application → Pages → Connect to Git → + Add account), as Cloudflare documents, and confirm the check answers 200 afterwards. Then add a build token under the Cloudflare card with a user API token made from the pre-filled link (or Cloudflare's _Edit Cloudflare Workers_ template): Shipcel checks it with `GET /user/tokens/verify` and registers it with `POST /accounts/{id}/builds/tokens` (Workers CI Write on the OAuth grant), keeping no copy. Confirm it's listed and that a build runs with it: a Cloudflare community report says tokens registered through the API can fail at the build's environment setup. Also verify account selection and repository listing. If Cloudflare rejects the grant type, adding an OAuth scope does not necessarily solve it. The integration then needs a supported authentication/build-provider adapter; do not enable the feature or claim automatic deployment works.

## Recovery and revocation

- A timed-out provider mutation is marked `needs_attention`; Shipcel never repeats it on its own. A workspace owner can choose **Check Cloudflare and resume**: Shipcel looks up the recorded Worker, build trigger, or initial build, adopts what exists, and repeats a request only when Cloudflare shows it did not take effect. It refuses a Worker older than the deployment and stops when duplicate Shipcel triggers exist; resolve those in Cloudflare first. Reconnected accounts are accepted only for the same Cloudflare account and repository. Do not delete production resources to clear a UI error.
- Removing a project/disconnecting does not delete apps, provider triggers, databases, or storage. Native automatic deployments continue until disabled in Cloudflare.
- Disconnect removes local ciphertext immediately. Revoke the OAuth/GitHub grant separately in the provider dashboard. Upstream revocation is not automated yet.
- A changed membership, repository permission, selected account, or replaced provider grant stops queued Shipcel work. In-flight provider operations may still complete and need inspection.
- A stuck initial build exits Shipcel monitoring after 45 minutes. Recovery starts a new 45-minute window and re-reads the build; a failed homepage check can also be repeated this way.
- Key rotation currently requires disabling connections/jobs, rotating the key, removing unusable saved grants, and reconnecting accounts. Transparent multi-key rotation and an operator reconciliation UI are remaining production milestones.
