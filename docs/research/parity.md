### A2. Can Access protect workers.dev and preview URLs?

**Yes.**

- **How to switch it on:** in the Worker's Access tab, choose "Protect this Worker behind Access" and pick previews only or all traffic. An account-wide "Protect all Workers" option also exists. Protection covers workers.dev, Version URLs, Preview URLs and Deployment URLs.
- **Requirement:** "Zero Trust enabled on your account".
- **Reading the user's identity:** the Worker gets it through `ctx.access`, with no manual JWT parsing.
- **Caveats:**
  - Worker-level Access policies **do not support WebSockets**.
  - `ctx.access` does not pass through Service Bindings or RPC.
  - If you turn off workers.dev in the dashboard but don't set `workers_dev = false` in config, it comes back on at the next deploy.
- **Seats:** every reviewer who signs in uses one of the 50 free seats.
- **Sources:** https://developers.cloudflare.com/workers/configuration/cloudflare-access/ · https://developers.cloudflare.com/workers/configuration/routing/workers-dev/

### A3. Static assets Direct Upload API (deploying without Wrangler)

**Steps:**

1. `POST /accounts/{account_id}/workers/scripts/{script_name}/assets-upload-session`. The Workers for Platforms variant is `.../workers/dispatch/namespaces/{ns}/scripts/{script}/assets-upload-session`. Send a manifest of `{path: {hash, size}}`, where the hash is 32 hex characters (the docs' example uses truncated SHA-256). It returns an upload `jwt` and `buckets`, which list only the files that are new or changed.
2. `POST /accounts/{account_id}/workers/assets/upload?base64=true`. Use `multipart/form-data` with base64-encoded file contents and `Authorization: Bearer <upload JWT>`, one request per bucket. The last upload returns a completion JWT.
3. Upload the Worker script with metadata `assets: { jwt: <completion token>, config: {html_handling, not_found_handling} }`, or use `keep_assets` to reuse the previous assets.

**Token lifetimes:** the upload JWT and the completion token are each valid for 1 hour.

**Limits:** 20,000 files per Worker version on Free (100,000 on Paid); 25 MiB per file; `_headers` 100 rules; `_redirects` 2,000 static plus 100 dynamic.

**Authentication:**

- The API reference accepts an **API Token** (Bearer) or the legacy API Email + Key.
- The required permission is "Workers Scripts Write". The newer role model calls this "Workers Editor".
- **OAuth is not listed on the endpoint's reference page.** Since 2026-06-03, Cloudflare lets developers create their own OAuth clients:
  - Only the Authorization Code flow is supported, with PKCE for public clients.
  - New clients are private; making one public requires domain verification and can't be undone.
  - The docs say OAuth scopes mirror API-token permissions, and give Wrangler deploying Workers as the example.
- My inference, which needs a live test: a properly scoped OAuth token should work with this endpoint.

**Sources:** https://developers.cloudflare.com/workers/static-assets/direct-upload/ · https://developers.cloudflare.com/api/resources/workers/subresources/scripts/subresources/assets/subresources/upload/methods/create/ · https://developers.cloudflare.com/workers/platform/limits/ · https://developers.cloudflare.com/workers/authorization/ · https://developers.cloudflare.com/changelog/post/2026-06-03-public-oauth-clients/ · https://developers.cloudflare.com/fundamentals/oauth/create-an-oauth-client/

### A4. Preview URLs

**Version URLs** (the older mechanism):

- Format: `<version-prefix>-<worker>.<subdomain>.workers.dev`, or with an alias, `<alias>-<worker>...`.
- They are **public when enabled**. They're on by default whenever workers.dev is on, and `preview_urls: false` turns them off. Cloudflare Access can protect them.
- **They are not generated for Workers that implement Durable Objects, Containers or Sandbox**, or for Workers for Platforms user Workers.
- No Workers Logs, tail or Logpush; workers.dev only (no custom domain); only the 1,000 most recent aliases are kept.
- Source: https://developers.cloudflare.com/workers/versions-and-deployments/version-urls/

**Worker Previews** (new, 2026-09-22):

- Created with `wrangler preview` (Wrangler 4.135.0 or later), or automatically by Workers Builds, which also **posts the URLs to PRs**.
- Each preview has a stable URL and an immutable per-deployment URL.
- **Durable Objects and Containers are isolated per preview automatically.** KV, D1 and R2 need separate bindings. Workflows and service bindings hit production, and queue consumers can't target a preview.
- Custom domains are supported. Previews are **public by default** and can be protected with Access; workers.dev URLs send `X-Robots-Tag: noindex`.
- Limits: 100 previews per Worker on Free (500 on Paid), 100 deployments per preview; the oldest are removed when you hit the cap.
- Cloudflare's docs say: "Do not use Version URLs for branch or pull request testing. Use Previews instead."
- Sources: https://developers.cloudflare.com/workers/previews/ · https://developers.cloudflare.com/workers/previews/compare-workflows/ · https://developers.cloudflare.com/changelog/post/2026-09-22-worker-previews/

## B. Netlify

### B1. `netlify deploy --allow-anonymous` and Netlify Drop

**CLI anonymous deploy** (added 2026-03-27; https://www.netlify.com/changelog/2026-03-27-create-and-deploy-anything-netlify-clis-improved-ax/):

- **What it does:** creates a project, deploys it and returns a live URL with no login or account.
- **How long it lives:** you have **one hour to claim it by logging in or creating an account. "After one hour, unclaimed projects are removed."**
- **After claiming:** the project takes the team's default project visibility.
- **How the claim link is delivered:** not stated.
- **Limitation:** sites that use serverless or edge functions need an account.
- Sources: https://docs.netlify.com/api-and-cli-guides/cli-guides/get-started-with-cli/ · https://docs.netlify.com/start/quickstarts/deploy-from-ai-code-generation-tool/ · https://cli.netlify.com/commands/deploy/

**Netlify Drop:**

- Logged out, files are published as-is with no build. Logged in, Netlify detects the framework and builds.
- **"If you drop without signing in, your project URL is protected with a temporary password until you claim it."**
- After claiming on credit-based plans with private-by-default switched on, the project stays private, and on Free/Personal only the Team Owner can see it. On legacy plans it becomes public.
- Size guidance: deploys under 50 MB work best; files over 10 MB may get stuck.
- **The claim window for Drop is not stated in the Drop docs.** Netlify's 2026-10-07 history post says:
  - In Jan 2022 the window was cut from 24 hours to one hour, with a cap of three anonymous sites per IP.
  - Anonymous drops have been password-protected until claimed since a 2024 fraud wave.
  - Unclaimed sites are suspended, then deleted a week later.
- Sources: https://docs.netlify.com/start/quickstarts/netlify-drop-quickstart/ · https://docs.netlify.com/deploy/create-deploys/ · https://www.netlify.com/blog/thirteen-years-of-netlify-drop/ · https://www.netlify.com/changelog/2026-07-27-netlify-drop-refresh/

**"Private until you publish":**

- The pricing page lists "Private by default until you publish".
- Teams created on or after **2026-07-28** on the credit-based Free, Personal or Pro plans default to "Private for new projects", enforced by Netlify login.
- A "Make public" button appears after the first successful production deploy.
- Previews (Deploy Previews, agent-run previews and branch deploys) stay private unless changed.
- Legacy, Enterprise and Open Source plans don't have this setting.
- Sources: https://www.netlify.com/pricing/ · https://docs.netlify.com/manage/security/secure-access-to-sites/project-visibility/ · https://www.netlify.com/changelog/2026-07-28-start-with-private-project-urls/

**Integrator claim flow:** tools that deploy for users generate a site claim token, which gives the user a claim URL. An optional `claim_webhook` notifies the tool when a claim happens, and the user picks which team to claim into. Sources: https://www.netlify.com/changelog/site-claiming-webhook-support/ · https://www.netlify.com/changelog/team-selection-for-claimed-sites/

## What this means for Cloudcel

- **Free-plan parity is now realistic** for cron, queues, workflows, AI, vector, Postgres pooling, analytics, Turnstile and Access (up to 50 users).
- **These still need Workers Paid or a third party:** Containers, Sandboxes, Dynamic Workers, Workers for Platforms, and sending email to arbitrary recipients. The last one matters for the sign-in service's magic-link or verification emails.
- **Version URLs won't work for Cloudcel apps that use Durable Objects**, such as the realtime channels. Worker Previews (Sept 2026) are the documented path for per-PR previews: Durable Objects are isolated and PR comments come through Workers Builds. KV, D1 and R2 still need separate bindings per preview.
- **Billing changes to plan for:**
  - Workflows step billing from 10 Aug 2026.
  - Observability ingestion pricing from 1 Dec 2026.
  - Supabase's Data API `GRANT` change on 30 Oct 2026, if customers use Supabase.
- **OAuth (June 2026) could replace user-pasted API tokens**, but the direct-upload endpoint only documents API tokens. Test it before building on it.

The Vercel plugin's MCP server needs authorising through `/mcp`; I didn't need it for this research.

## D. Vercel's CLI, command by command (15 Oct 2026)

Source: [Vercel CLI overview](https://vercel.com/docs/cli), last updated 7 Oct 2026, which lists 69 commands. Compared with `cloudcel` 0.4.0 (`packages/cli/src/cli.ts`). Verdict: **level on the everyday loop, not on the whole CLI.**

**Update, 23 Oct 2026:** `firewall` is now `cloudcel security`: Cloudflare's Free Managed Ruleset, Bot Fight Mode, AI crawler blocking, Under Attack mode, rules by country, IP address or path, and a rate limit, for the zones of an app's custom domains (tested against a stand-in for Cloudflare, not yet a live zone). Now **46 equivalent, 3 partial, 20 missing** (9 that Cloudcel could add).

**Update, 21 Oct 2026:** added since: `tokens` (add approved in the browser), `teams ls`, `usage`, `alerts`, `webhooks ls`, `pricing`, `blob` (as `storage`), `dns`, `cache purge`, `redirects` (a `_redirects` file applied with the next deploy, not instantly) and `bisect`. Now: **45 equivalent, 3 partial** (`teams`: listing only; `webhooks`: listing only; `target`: preview and production only), **21 missing** (10 that Cloudcel could add: `routes`, `traces`, `deploy-hooks`, `certs`, `security`, `comments`, `flags`, `guidance`, `setup`, `firewall`; 11 that are Vercel's own products). The lists below are as they were on 15 Oct.

- **Equivalent in Cloudcel (36):** `deploy` (default, `--prod`, `--target`, `--prebuilt`), `build`, `dev`, `promote`, `rollback`, `redeploy` (GitHub projects), `list`, `inspect`, `logs` (`--since`, `--errors`, `--follow`), `open`, `rolling-release`, `metrics`, `curl`, `httpstat`, `init` (starter kits), `link`, `git`, `project`, `remove`, `env` (ls, add, update, rm, pull), `pull`, `domains` (ls, add, rm), `alias`, `crons` (ls, add, rm), `activity`, `login`, `logout`, `whoami`, `switch`, `mcp`, `agent`, `api`, `upgrade`, `help`, `signup` (signing in with GitHub creates the account), `telemetry` (nothing is collected).
- **Partial (6):** `teams` (says which workspace; teams are managed in the dashboard), `usage` (`cloudcel budget` gives one app's cost this month, not the account's), `target` (preview and production only; no custom environments), `alerts`, `tokens` and `webhooks` (all in the dashboard, not the CLI).
- **Missing, and possible for Cloudcel (16; check Cloudflare's current documentation before building each):** `bisect`; `blob` (R2 and KV storage); `cache` (purging a custom domain's cache); `dns`; `firewall` (WAF custom rules, rate limiting); `redirects` (`_redirects` in static assets, or Bulk Redirects); `routes`; `traces` (Workers traces); `deploy-hooks`; `certs`; `security` (checks of the account's setup); `comments` (preview comments, which Cloudcel would have to build); `flags`; `pricing` (Cloudcel's and Cloudflare's plans); `guidance`; `setup` (agent setup; `mcp` and `agent init` cover part of it).
- **Missing, Vercel's own products (11):** `ai-gateway` (Cloudflare has an AI Gateway of its own), `buy`, `connect`, `contract`, `global-config` (Edge Config), `install` and `integration` (marketplace), `microfrontends`, `sandbox`, `skills`, `vcr` (container registry).
- **Differences inside shared commands, from the platform:** `env pull` writes secrets' names without values (Cloudflare never returns a secret's value); `crons run` explains that Cloudflare has no call that triggers a schedule (use `cloudcel dev` and `/cdn-cgi/handler/scheduled`); `domains` has no `buy`, `price` or `check`.
- **The largest ease-of-use gap isn't a command:** `npm i -g vercel` then `vercel login` works for anyone, while `cloudcel` is installed from a Cloudcel's own address (`npm install -g https://your-cloudcel-address/cli/cloudcel.tgz`, then `cloudcel login --url …`). Closing it needs a hosted Cloudcel and the CLI on npm, which are owner decisions ("What's next" item 8 in `HANDOFF.md`).
